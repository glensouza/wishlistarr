# Parent notifications

Open **Parent area → Notifications** to save the public Wishlistarr origin, then configure ntfy, Discord, Apprise, or SMTP. Each provider has its own enabled switch, event selection, and **Send test** button. Save changes before testing. Tests send immediately even when a provider is disabled. The public origin is used for links; request Host headers never determine notification destinations.

Subscriptions belong to the signed-in parent account. Version 1 has one server-owner parent and no invitations or additional roles. API keys and trusted-network access represent that owner only while exactly one parent exists. Signed approval links always require the recipient's parent login session.

- **ntfy:** Enter the full topic URL, such as `https://ntfy.example.invalid/private-topic`. An optional bearer token is supported. Messages are UTF-8 plain text sent by POST to that topic.
- **Discord:** Enter the complete webhook URL. Existing query parameters such as `thread_id` are preserved. Delivery waits for Discord confirmation, disables mentions, and suppresses embeds.
- **Apprise:** Enter the complete notification endpoint: `/notify/` for stateless delivery or `/notify/config-key` for a saved configuration; a proxy path prefix is supported. Stateless target URLs are optional and sent as `urls` only when configured. If no targets are configured, the `urls` field is omitted so the server can use `APPRISE_STATELESS_URLS`; the server must have defaults configured. A saved-configuration endpoint never receives `urls`, and saving that endpoint clears inapplicable local targets. This avoids version-dependent handling of unused `urls` fields, including stricter validation in Apprise API 2.0.0. HTTP 200 indicates success; redirects and partial failures are failures. Deployments requiring HTTP Basic authentication are not currently supported.
- **SMTP:** Configure host, port, sender and recipient. **STARTTLS** upgrades the connection and validates the server certificate; SMTP authentication requires it. Implicit TLS on port 465 is not supported. Unauthenticated local relays may disable STARTTLS. No system credentials are used. Delivery uses the SMTP client built into .NET. Microsoft no longer recommends it for new work because it lacks modern protocols such as implicit TLS and OAuth sign-in, but it supports STARTTLS with certificate validation and plain authentication, which covers this one-message-at-a-time use without adding a dependency. The subject is fixed and the sender and recipient are validated single addresses, so request titles never reach mail headers. A blank port uses 587.

Messages name the kid and the title, for example "Ada asked for Spirited Away. It is waiting for your approval." Titles are read through the same retention check as the rest of the app, so a title older than the TMDB retention is fetched again or replaced by the request number; delivery records store only the request number and event, never the title. Test failures and saved delivery errors give the HTTP status and a plain reason, such as rejected credentials (401 or 403), a missing endpoint (404), a redirect or rate limiting (429). Provider response bodies are never shown or stored.

Provider configuration is encrypted with the application's existing Data Protection keys. Secret fields and HTTP destination URLs are masked in responses. Empty secret inputs preserve saved values. Keep the database and encryption keys together when backing up or restoring the application. Use HTTPS for externally reachable endpoints.

Request events include pending, approved, denied, available, and failed. Repeated PIN failures and profile locks are also selectable. New subscriptions start with future request events. Disabling a subscription cancels queued notifications when the delivery job next runs. A pending notification is only sent while the request is still waiting: requests that were auto-approved, already in the library, granted by a parent, or decided before delivery are skipped instead of announcing a decision that no longer needs one. Their other events, such as approved or available, are still sent to subscriptions that selected them. Delivered messages necessarily leave the application and are subject to the destination service's retention settings.

## Browser notifications

On the same notifications screen, **Turn on notifications** subscribes this browser. Wishlistarr gives the browser its public signing key. The browser then saves a push subscription for the signed-in parent: the endpoint and the keys that encrypt a message for that browser. The list shows only that a browser is saved. It does not show the endpoint or those keys. Removing a browser stops messages to it. A kid session cannot add, list, or remove a parent's browser.

The private signing key is created once, protected with the same data protection keys as other secrets, and stored in the database. It is not sent to the browser and it is not written to the log. A backup restores it with the database, so the public key stays the same. See [backup.md](backup.md).

The service worker that shows the notification is served with the built frontend at `/sw.js`. A browser that cannot show notifications, or that has blocked them, gets a plain message and nothing is saved.

Messages for a subscribed browser use the same request events as the other providers, and the same PIN and lock notices. The text is encrypted to that browser and signed with the application key. A subscription the push service reports as gone (HTTP 404 or 410) is removed. A rate limit (HTTP 429) is retried, and a `Retry-After` delay longer than the next step is honored up to 60 minutes. A rejected signature (HTTP 401 or 403) is retried and does not delete the browser. Attempt limits match the other providers.

Kid devices subscribe separately, as described in [kid-devices.md](kid-devices.md). A notice on a signed-in kid's own screen is described in [kid-home.md](kid-home.md).

## Approval links

Pending notifications contain signed approve and deny links. Both choices share a single grant bound to the request and recipient, valid for 48 hours from first delivery preparation. A GET only renders a confirmation page: previews, unfurlers and repeated opens cannot consume a link or decide a request. If the browser is signed out, open parent sign-in and then use **Continue after signing in** on the confirmation page. A signed-in browser may also need this step when arriving from another site because the login cookie uses SameSite Strict.

Only the intended parent's authenticated, antiforgery-protected POST can consume the grant. API keys and trusted-network access can open the confirmation page but only see the sign-in step, and their POSTs are refused. The grant is claimed in the same database statement that checks the request is still pending, so a request decided in the parent area at the same moment leaves the link unused and the page reports that it is no longer available. If the approval service still finds the request decided after the claim, the page says it was decided elsewhere instead of reporting a saved decision. The confirmation explicitly identifies the request number and action. The decision uses the same approval service as the parent request queue. Replays, changed tokens, expired grants and already-decided requests are rejected. If processing fails after consumption or the application stops at that point, review and retry the request in the parent area; the link stays consumed. Pages forbid caching, embedding (`frame-ancestors 'none'` and `X-Frame-Options: DENY`) and referrer disclosure.

## Delivery and retries

The `notifications` background job runs every minute by default and can be triggered through the existing Jobs API. It also starts at once when a kid's request starts waiting for a parent and when a PIN failure or profile lock is queued; a start while it is already running makes it run once more afterwards. Other request events wait for the next scheduled run. Queuing a PIN or lock notification never fails the kid's sign-in attempt: a database error is logged instead. Request history acts as the durable event source. The job stores delivery records and its per-subscription event cursor in one database transaction, then sends queued records. PIN/security events are queued when raised. Each record has at most eight delivery attempts, with delays of 1, 2, 4, 8, 16, 32, and 60 minutes. When a service answers 429 with a `Retry-After` delay longer than the next step, the job waits that long instead, up to 60 minutes. Discord messages are shortened to its 2,000 character limit, keeping both approval links intact. The last failed attempt is logged as an error. A failure logs only the delivery ID, provider and attempt; provider response bodies, destinations and credentials are not logged. Failed manual test sends return a safe error and are not automatically retried.

Successful, skipped, cancelled or exhausted delivery records are removed 30 days after they were queued. Exhausted records are retained during that period for diagnosis; fix the configuration and use the test button to confirm recovery. Delivery is at least once: if a destination accepts a message before the process stops or the response is lost, a retry can duplicate that message. Its approval links still share the same single-use grant. The application should run as a single instance against its SQLite database, as required by the existing job runner.
