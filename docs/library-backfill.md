# Library backfill labels

In the parent area, open **Library labels** and choose a kid profile. The preview checks movies and shows already in the selected Plex server's library against the same content policy evaluator used for kid browsing. A full [library refresh](library.md) must have completed for that server first. Unmatched titles remain visible in the preview with a metadata-unavailable reason, but cannot be selected.

The preview groups items into **Allowed**, **Needs review** and **Blocked**, with policy reasons. Only allowed items start selected. A parent can exclude these or explicitly include review and blocked titles; selecting those is an intentional override for Plex label access, like a parent grant. This does not change the profile's policy. Each Plex copy is listed separately. Selection is retained across preview pages, and changing profiles clears it. Reopening refreshes the preview: apply and dry run remain unavailable until that refresh succeeds. A failed refresh cannot submit an older preview. If a refreshed title changes into a review or blocked category, it is deselected so access needs fresh parent consent; this also applies to its previously visited copies on other pages. Explicit overrides are preserved when the decision is unchanged. The preview reads metadata but changes neither Plex nor the database. Metadata failures leave the affected titles unselectable. Policy lookups share the approval queue's 5 second lookup and 12 second page budgets; titles that cannot be checked in time are reported as metadata unavailable.

**Dry run selected labels** validates the selected items, selected server and profile label without creating a batch, running a job, writing ledger entries or writing to Plex. **Apply selected labels** stores the selection and queues the `library-backfill` job. Its default schedule is every 30 seconds, with up to 25 items processed per run, one at a time. Apply and undo share a gate, so they cannot run over one another. Progress is saved after every item and pending work resumes after a restart. If the schedule is disabled, a parent can run the job manually to process the next chunk.

Each write uses the existing Plex label writer to retain other labels, lock the field and verify the result. Before writing, it checks the selected server and the item's guid against the selection. Profile label assignments and each backfill write share a gate through the read, confirmation, write and verification steps, so another profile cannot take the label between the ownership check and the Plex change. Ledger cleanup uses the same gate. Content imports acquire it before their database transaction so waiting for a label write cannot hold the database's write lock. Items deleted or rematched since preview are skipped rather than labeling a different title. A changed server, archived profile or changed profile label pauses an apply. Service failures and timeouts pause the batch with a specific message; **Resume** retries pending items. Timed-out writes may already have reached Plex, so a retry reconciles current labels instead of assuming the write failed.

The label ledger reservation and that copy's batch ownership claim are saved together before Plex is touched. Every applied label therefore has a ledger entry with source `backfill:<batch id>`, including a write interrupted before progress could be saved. Existing labels and ownership from outside the batch are preserved. A label already on one copy remains outside the batch even when another copy shares its guid. The guardian repairs backfill labels only on unchanged copies with durable ownership claims, during apply and after completion; it never expands a batch's selection to pending unclaimed copies or excluded copies with the same guid. A later request or explicit grant takes ownership of an existing batch label so undo preserves that later authorization.

**Undo** stops pending apply work and queues a resumable removal of only the labels that batch owns. It can also undo a partial or paused apply. The original server must be selected; undo remains possible after the profile is archived or renamed. If another active profile now uses that label, undo pauses and preserves both its current labels and the ledger. This is checked again for each copy and before ledger cleanup, including after resuming a partially completed undo. Change the newer profile's label before resuming. Undo marks the ledger source `undo:<batch id>` before removing labels. The guardian neither follows nor restores these rows while removal is pending, including immediately after undo is requested, between chunks and after a restart. Once every owned copy is processed the marker rows are removed. A rematched or missing identity is skipped and its ledger marker is retained for inspection; batch results report these skips and the parent must resolve them in Plex. Other labels, pre-existing copies and ownership reassigned to a later grant are preserved. A completed undo can be requested again safely.

Plex has no conditional label update. The writer's second read and post-write verification reduce interference from edits made elsewhere, but cannot make a Plex edit and the local database one transaction. If an item is removed and added back with a different rating key, this batch skips it instead of guessing a replacement. Preview again to include its new identity.

## Parent API

All routes are under `/api/v1/labels/backfill` and require parent authorization. Cookie sessions also require the usual antiforgery header for mutations.

- `GET /preview?kidProfileId=1&offset=0` returns `{ kidProfileId, serverId, label, items, total, offset, limit }`, with 100 items per page. Items contain `libraryItemId`, `guid`, Plex `title`, `kind`, `tmdbId`, `outcome`, structured policy `reason` and `selectable`. `needsApproval` is displayed as “Needs review”. A negative offset is `400`, an absent or archived profile is `404`, and an index that is not ready for the selected server is `409`.
- `POST /batches` accepts `{ kidProfileId, serverId, label, items: [{ libraryItemId, guid }], dryRun: false }`. Select 1 to 10000 different resolved items. Stale server, label, guid or index identities return `409`. A dry run returns `200` with `{ dryRun: true, selected }`; apply returns `202` with a batch summary and its status URL.
- `GET /batches` lists the newest 50 batch summaries. Each includes its id, profile id, label, state, creation time, error and item counts: `total`, `pending`, `applied`, `preserved`, `skipped`, `undone`.
- `GET /batches/{id}` returns `{ batch, items }`, including per-item states and explanations. These titles come from Plex; no TMDB title text or other metadata is stored by backfill.
- `POST /batches/{id}/resume` returns `202` and resumes a paused apply or undo.
- `POST /batches/{id}/undo` returns `202` and queues undo from saved ownership claims. Unknown batch ids return `404`.

Batch states are `applying`, `paused`, `completed`, `undoing`, `undoPaused` and `undone`. Per-item states are `pending`, `applied`, `preserved`, `skipped` and `undone`. Batch history is retained so a parent can inspect or undo old operations.

The feature adds no Plex wire protocol. Label replacement, locking, removal and guid identity reads use the existing integration, following [python-plexapi's label editing API](https://python-plexapi.readthedocs.io/en/latest/modules/mixins.html#plexapi.mixins.LabelMixin). Show labels target the show, as described in [Plex labels](plex.md#labels). Preview uses TMDB details and [movie release dates](https://developer.themoviedb.org/reference/movie-release-dates) or [TV content ratings](https://developer.themoviedb.org/reference/tv-series-content-ratings) through the existing policy pipeline.
